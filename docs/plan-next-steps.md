## 4. 步 B · 桌面壳与全局热键（M1 前半）

**目标**：`Ctrl+Alt+Space` 在任何程序里按下去，快记窗立刻出现；输入完窗口消失，**原来的编辑位置不丢**。

### B0 前置：安装工具链（约 4–6GB，15–30 分钟）

| 要装 | 用途 | 状态 |
| --- | --- | --- |
| **Rust 工具链**（rustup，`x86_64-pc-windows-msvc`） | Tauri 的内核 | ✅ 已装 **1.99.0** |
| **MSVC 生成工具**（VS 2022 Build Tools，勾「使用 C++ 的桌面开发」） | Rust 在 Windows 的链接器 | ✅ 已装 |
| WebView2 | 界面渲染引擎 | ✅ 已装 154.0.4258.53 |

**工具链验证方式（不要只看版本号）**：实际编译并运行一个 Rust 程序 ——
只查 `rustc --version` 发现不了链接器问题（`link.exe not found` 只在真正链接时才暴露）。

### B1 架构决策：Node 内核怎么进桌面壳（未决项 D3）

Tauri 壳是 Rust + WebView，而内核是 Node。有三种接法：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **B1-a 独立 Node 进程** | 外壳拉起系统已安装的 Node | 内核**零改动**；崩溃互不影响 | 要求目标机器已装 Node —— **分发场景下不成立** |
| **B1-b Node 随包** | 把 Node 运行时与内核作为**资源**打进安装包，外壳从资源目录拉起 | **用户无需装 Node** | 安装包 +30–40MB |
| B1-c 内核搬到 Rust | 用 Rust 重写数据层 | 单进程、最省内存 | **等于重写整个已验证的内核**，342 项测试全部作废 |

**决策：分两种场景，共用同一份内核代码**（用户确认要"打包安装运行"，因此 B1-b 是必需项）：

| 场景 | 用哪个 | 理由 |
| --- | --- | --- |
| **开发时** | **B1-a**（系统 Node） | 改内核后无需重新打包，迭代快 |
| **打包分发** | **B1-b**（Node 随包） | 用户双击安装就能用，不需预装任何东西 |

> **为什么明确否决 B1-c**（用户曾问"是不是要先移植到 Rust"）：
> 内核是**342 项测试验证过**的资产，用 Rust 重写等于把它全部作废；
> 而换壳真正需要的只有三件事 —— **拉起子进程、注册全局热键、开无边框窗**，
> 三件都不需要碰数据层。等将来真有性能或分发的硬需求，再单独评估。

**为什么用"资源"而不是 Tauri 的 sidecar（`externalBin`）**：
两者差别只在"谁负责找路径"。sidecar 要额外装 `tauri-plugin-shell`、配 `externalBin`、
并在构建时按目标三元组重命名文件；资源方式只是把 Node 可执行文件放进资源目录，
外壳用 `Command::new(<资源目录>/node/node.exe)` 拉起 —— **依赖更少、路径更透明**。
Node 是 MIT 许可，随包分发没有问题。

#### B3 的一个已知缺陷（✅ 已在 B3-4 解决）

**症状**：快记窗保存后不隐藏，停在被 `.closing` 设成透明的状态 —— 用户看到**黑屏**。

**根因**：`capture.js` 靠 `window.close()` 收窗。那在浏览器里是对的（它的注释也写着
"只有由脚本打开的窗口才允许被脚本关闭"），但 **Tauri 的 WebView 不认这句** ——
窗口是 Tauri 建的，不是 `window.open()` 开的。

**试过并失败的三种 Tauri 侧方案**（都**静默失败**，没有报错）：

| # | 方案 | 失败表现 |
| --- | --- | --- |
| 1 | `setup()` 里 `eval()` 替换 `window.close` | 页面已拿到原生引用，替换太晚 |
| 2 | `WebviewWindowBuilder::initialization_script` 注入替身 | 可见性时间线证明脚本从未执行 |
| 3 | 轮询 DOM 读 `.closing` 类 | `eval_with_callback` 的回调从未触发 |

**诊断得到的确定结论**：

| 窗口 | 创建方式 | JS 通道 |
| --- | --- | --- |
| 主窗口 | **配置声明 + 应用协议** | ✅ 正常 |
| 快记窗（当时） | **运行时创建 + 外部 http URL** | ❌ 不可靠（`eval` 返回 Ok 但实际不执行、回调不触发） |

**解法（B3-4）**：把快记窗也改成 `WebviewUrl::App("capture.html")` ——
与主窗口**同一条加载路径**。三种方案里最简单的那种（方案 2 的替身）随即生效。

**实测**：

| 路径 | 结果 |
| --- | --- |
| `Enter` 保存 | ✅ 内容入库，**窗口自动收起** |
| `Esc` 取消 | ✅ 窗口收起 |
| 再次唤出 | ✅ 复用（不必重新创建） |
| 浏览器开发（`/capture` 由 Node 提供） | ✅ 照常，页面一个字符未改 |

#### 关闭之后暴露的第二个缺陷：复用窗口会残留状态（用户实测发现）

用户报告："**enter 确认后快记板维持在关闭状态，esc 退出和 ctrl+alt+space 呼出都能用，
但保存一次后再次呼出不能写入了**"。

**根因**：为了复用（省掉 380ms 的 WebView2 初始化）窗口只 `hide()` 而不销毁，
**页面没有销毁**，于是两处状态残留：

| 残留 | 后果 |
| --- | --- |
| `.closing` 类（`opacity: 0` + 动画 `forwards` 保持） | 再唤出时**看得见框、看不见内容** |
| `capture.js` 的模块级 `finished = true` | 保存逻辑开头就是 `if (finished) return` → **再也不能写入** |

**修法：每次唤出时 `location.reload()`**，把这两处（以及将来任何新增的模块级状态）
一次性归零。

> **为什么选重载而不是加"重置钩子"**：重置钩子要逐项列出需要清什么，
> 而**每加一个模块级状态就可能漏一处** —— 那正是本项目第一类错误
> （同一规则/状态写在两处必然背离）的形态。重载不需要维护这份清单。
>
> **代价**：每次唤出多一次页面加载（本地资源，实测无感知）。
>
> **实测**：连续两轮"热键 → 写入 → Enter"都成功（`round-1`、`round-2` 均入库），
> 此前第二轮必然失败。

**同时加了兜底关闭按钮**（右上角红色 ×，静态写在 `capture.html` 里）：
浮窗无标题栏、没有系统关闭按钮，而"保存后自动收起"与 Esc 都依赖页面脚本正常 ——
脚本一旦出问题就**只能去杀进程**（实测遇到过一次）。
它复用同一个 `window.close()`，因此不引入第二条关闭路径。


> **这一段的真正教训**：三个"看起来都对"的方案连续静默失败时，
> 该怀疑的是**前提**（"这个页面有 JS 通道吗"），而不是继续换手法。
> 主窗口与快记窗唯一的结构差别就是加载方式 —— 那个差别才是根因，
> 而它一直摆在眼前。

### B 的完成判据

在任意程序里按 `Ctrl+Alt+Space` → 输入 → `Enter` → 窗口消失且**原程序光标位置不变**，
端到端 ≤ 500ms。这一条通过，就可以开始"初步体验"了。

| 1 | **自带 Node 运行时** | 打进安装包（+30–40MB）。用户不需要装任何东西 |
| 2 | **数据默认 `%APPDATA%\WorkHelper`，但可配置** | 安装到 `Program Files` 后程序目录不可写，因此不能放程序目录旁 |
| 3 | **界面随包自带，只有 API 走 Node** | 界面瞬间打开、零延迟；快记窗不再受"Node 正在启动"影响 |
| 4 | **NSIS 安装包** | 有开始菜单与卸载项，可选开机自启 |
| 5 | **首次启动显示主窗口** | 装完双击就能用，不让人以为没装上 |

### 3 与 4 引出的两个连带改动（不是可选项）

**① 界面与 API 会变成跨源，必须加 CORS**

```
界面  tauri://localhost/index.html      ← 安装包内
API   http://127.0.0.1:7317/api/...     ← Node 服务
```

两者**不同源**，浏览器规则要求 Node 返回 CORS 头，否则所有数据请求被拒。
WebView2 同样适用这条规则。做法：`src/ui/server.ts` 只对**自家源**返回
`Access-Control-Allow-Origin` 并处理 `OPTIONS` 预检。因为服务只监听 `127.0.0.1`，
外部本来就不可达，这是安全的。

**② `api.js` 必须知道服务器地址**

现在它用相对路径 `/api/...`（与 Node 同源所以能工作），界面自带后必须改成显式地址。
做法：**外壳启动 Node 后把端口注入页面**，`api.js` 读注入值；读不到就退回
`location.origin`（**浏览器里开发时行为完全不变**）。

### 4.1.5 B3-3 实施记录（已完成并实测）

**先做了一个决定性实验**：把 `src/` 树复制到别处、用同一份 Node 运行 ——
**独立可用**（`/api-base`、界面、数据接口全通），**不需要 `node_modules`、
不需要 typescript 包**。这扫清了打包的最大不确定性，也印证了"零依赖 + Node 原生跑 TS"
这个设计在分发场景下同样成立。

**资源组成**：

| 内容 | 大小 | 来源 |
| --- | --- | --- |
| `node/node.exe` | **99.9 MB** | 系统 Node（`node --version` 自检） |
| `src/` 整棵树 | **439 KB** | 仓库 `src/`（57 个文件） |

**整个"安装目录"实测 112.4 MB。**

**`scripts/prepare-resources.mjs`** 负责生成资源目录，并已挂到
`tauri.conf.json` 的 `beforeBuildCommand` —— **不手动跑也不会漏**（漏了会构建失败，
而"忘了跑一个手动步骤"正是本项目的常见失误形态）。
脚本自带两项自检：入口文件存在、**随包 Node 能真的跑起来**（复制损坏要在这里发现，
而不是装到用户机器上）。

**资源目录整体不进版本库**（`.gitignore` 里 `*` + `!.gitignore`）：
`node.exe` 100MB 提交会让仓库膨胀；`src/` 已被版本库跟踪，再存一份就是同一内容两个副本 ——
那正是第一类错误（同一规则写在两处）。

#### 判据踩的第三个坑（值得单独记）

`detect_dev_mode()` 前后错了两版，都是"在开发机上测不出来"的类型：

| 版本 | 判据 | 为什么错 |
| --- | --- | --- |
| v1 | 从可执行文件向上找 `shell/src-tauri/Cargo.toml` | `target-dir` 在 `D:/cargo-target/`，与仓库根**没有共同祖先** |
| v2 | 编译时注入的仓库根**是否存在** | **更隐蔽**：打包产物是在开发机上构建的，那个路径在构建机上**当然存在** → 打包版永远被判成开发态、永远用系统 Node。**在开发机上永远测不出来，装到别人机器上才炸** |
| **v3 ✅** | 可执行文件旁边有没有 `resources/src/ui/main.ts` | 安装布局独有，与环境变量、构建路径、当前目录**都无关** |

**教训**：判据要选**与构建机无关的客观事实**。"编译时注入的路径是否存在"
看起来可靠，实际把"构建环境"和"运行环境"混为一谈了。

#### 自包含验收（实测）

| # | 验收项 | 结果 |
| --- | --- | --- |
| 1 | 模拟安装目录启动 | 形态=打包态、随包 Node、数据目录 `%APPDATA%` ✓ |
| 2 | **内核进程的 `ExecutablePath`** | `...\resources\node\node.exe` —— **证明用的是随包 Node** ✓ |
| 3 | 移走随包 `node.exe` | **明确报错**："打包形态下找不到随包的 Node……建议重新安装" ✓ |
| 4 | 开发态回归 | 形态=开发态、用系统 Node、数据目录仍是仓库 `data/` ✓ |

> **第 2 条是这次最有力的证据**：直接读进程的可执行文件路径，
> 比"把系统 Node 改名"之类的间接手段确定得多。

### 4.1.4 B3-2 实施记录（已完成并实测）

**默认数据目录按形态区分**（这是实施中才想清楚的一点）：

| 形态 | 默认数据目录 | 理由 |
| --- | --- | --- |
| **开发态** | 仓库的 `data/` | 保持开发者已有数据；也才符合"浏览器里开发照旧"这个验收标准 |
| **打包态** | `%APPDATA%\WorkHelper\data` | 安装目录不可写，必须换地方 |

> **我第一次写错了**：两种形态都用 `%APPDATA%`，于是外壳一启动就建了一个空库、
> 看不到已有数据 —— 表现正是"我的数据不见了"。
> **是启动日志（形态 + 数据目录）把它暴露出来的**，不是测试。
> 这也是把"解析出的路径一律打印出来"的价值。

**用户覆盖的存放位置**：`%APPDATA%\WorkHelper\config.json` 的 `dataDir` 字段。

- **为什么不放在数据目录里**：数据目录本身可被改，把"数据目录在哪"记在数据目录里
  就成了循环依赖 —— 改完下次就找不到配置。
- **为什么不放在程序目录旁**：程序目录可能不可写，而"我想改数据目录"这件事
  **恰恰可能就是因为程序目录不可写**。
- 配置文件不存在或格式不对时**退回默认值并继续** —— 一个坏掉的配置不该让程序起不来。

**实现要点**：

| 点 | 做法 |
| --- | --- |
| 数据目录由外壳显式传给内核（`--data`） | 不靠内核自己推导，避免它算出 `Program Files` 里的路径 |
| **实际写文件验证可写性** | 只查 `is_dir()` 会漏掉"目录在但只读"，那要等到建库时才失败，错误还指向数据库而不是权限 |
| 开发/打包判据用**编译时注入的仓库根** | `target-dir` 在 D 盘独立位置，**从可执行文件上溯永远找不到仓库**（本文件已栽过三次），判据一律以编译时注入为准 |
| 不引入 JSON 依赖 | 只认一个字段，手写解析对固定形状足够可靠，符合项目的零依赖约束 |

**实测**：

| 场景 | 结果 |
| --- | --- |
| 开发态默认 | 形态=开发态、数据目录=`D:\projects\WorkHelper\data`、读到 7 条资料 ✓ |
| 配置覆盖 | 写 `config.json → D:\temp\wh-alt-data` 后重启，库确实建在那里 ✓ |
| 判据错误时的行为 | 曾误判为打包态 → **明确报错说缺内核资源**，而不是静默失败 ✓ |


### 4.1.3 B3-1 实施记录（已完成并实测）

**改动清单正好是预告的四层，一层不少**（这正是第二类错误要求的"清单动作"）：

| 层 | 改动 |
| --- | --- |
| `tauri.conf.json` | 加 `build.frontendDist`，主窗口 `url` 从 `http://127.0.0.1:7317/` 改为 `index.html`（走应用协议） |
| `src/ui/server.ts` | 加 CORS 头 + **OPTIONS 预检处理** + `/api-base` 端点 |
| `src/ui/static/api.js` | 地址改为**运行时发现**，不再用相对路径 |
| 静态资源路径 | **无需改动** —— 应用协议会**跳过开头的 `/`**，因此 `/app.js` 在两种加载方式下都正确 |

**关键技术判断（已查源码确认）**：`/app.js` 这类绝对路径在应用协议下解析为
`frontendDist` 根目录下的 `app.js`（asset.rs 里明确 `// skip leading /`），
因此 HTML 一个字都不用改。这消除了"两种加载方式需要两套路径写法"的隐患。

**端口只定义一处，前端运行时发现**：
原本端口要在 `server.ts` 与外壳各写一份（改一处必漏一处 —— 第一类错误）。
改为：前端先试**同源** `/api-base`（开发场景一次就成），
失败再试候选地址（打包场景），拿到后缓存。`/api-base` 由内核返回**它自己实际监听的**地址。

**实测证据**（开启内核请求日志 `WORKHELPER_VERBOSE=1`）：

```
GET     /api-base                      ← 前端发现 API 地址
OPTIONS /api/capture/listPending       ← CORS 预检
POST    /api/capture/listPending       ← 跨源数据请求成功
OPTIONS /api/planning/listProjects  →  POST ...
OPTIONS /api/tracking/focus         →  POST ...
OPTIONS /api/tracking/openTasksView →  POST ...
OPTIONS /api/system/trashOverview   →  POST ...
```

**验证方式的教训（第三类错误）**：最初想用"窗口标题是否变化"判断页面是否加载，
但**外壳给窗口设的标题与页面 `<title>` 恰好相同**，这个观测点**区分不出**任何东西。
改用"内核是否收到 API 请求"作为判据 —— 它同时证明了页面加载、地址发现、CORS、
数据取回四件事，是真正决定性的证据。
为此在外壳里加了 `WORKHELPER_VERBOSE=1` 开关，排查同类问题时可复用。


### 4.1.1 怎么验证"打包真的自包含"（不重开虚拟机/账户，不清 PATH）

**用户明确要求：在当前环境继续开发，非必要不重开虚拟机或账户、不清 PATH。**
这个要求是对的 —— 原来的方案（虚拟机/另一账户）成本过高，而且**验证得比需要的弱**：
虚拟机只告诉你"坏了"，不告诉你**坏在哪一项**。

**真正的风险不是"别的机器缺什么"，而是"我这台机器上的外部依赖掩盖了打包缺陷"。**
例如外壳的 `find_node()` 先查 PATH，那么**打包时漏掉 Node 也测不出来** ——
它会静默用系统的 Node 跑起来。

#### 措施一：让依赖无法隐藏（设计约束，不是测试技巧）

| 约束 | 理由 |
| --- | --- |
| **打包态只用随包 Node，完全不查 PATH** | 消除"静默回退到系统 Node"。找不到就报错，而不是悄悄用别的 |
| **不再硬编码 `D:\AppGallery\node.exe`**（当前代码里有） | 那是本机的临时位置，写死只会掩盖问题。开发态用 PATH 查找即可 |
| **数据目录由外壳显式传给内核**（`--data`） | 不依赖内核自己推导，避免"装到 Program Files 后不可写" |
| **界面资源路径在打包态解析到资源目录，找不到就报错** | 避免"编译时注入的仓库根"在打包后指向不存在的路径 |

#### 措施二：启动自检（缺什么就说什么）

外壳启动时按顺序检查，**任何一项不过就明确报错并退出**，不进入半可用状态：

| 检查项 | 失败时的提示要点 |
| --- | --- |
| 随包 `node.exe` 存在且可执行 | 说清期望路径；安装损坏 → 建议重装 |
| 内核资源树存在（`resources/src/ui/main.ts`） | 同上 |
| 数据目录**可写**（实际写一个临时文件验证） | 说清目录路径与失败原因（权限/只读盘） |
| 端口 7317 空闲 | 说清被哪个进程占用（若能取到），而不是静默换端口 |
| 界面静态资源可解析 | 同上 |

#### 措施三：`--diagnose` 打印全部解析路径

一条命令输出所有路径与检查结果，**它本身就是验证工具**：
比"界面能不能打开"精确得多，也让用户报障时能直接贴出来。

#### 验收标准（在本机就能做，且是决定性的）

```
1. 用打包产物启动 → 应正常
2. 把 D:\AppGallery\node.exe 临时改名 → 再启动打包产物 → 仍应正常
   ← 决定性验证：证明产物真的自包含
      （官方安装器不往 D:\AppGallery 放 Node，因此这不算"清理 PATH"）
3. 故意删掉资源目录里的 node.exe → 启动应明确报错"缺 node" → 证明自检有效
4. 恢复上述临时改动
```

**第 2 条是关键**：它证明打包产物不依赖任何外部 Node。**第 3 条**证明失败不会被静默吞掉。

## 8. 风险与依赖

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **Rust + MSVC 安装失败或耗时过长**（步 B 的唯一硬前置） | 全局热键做不出来，只能停在步 A | 步 A 全部完成后先验证工具链，再动 B 的代码；期间界面已可用，不算停滞 |
| `Ctrl+Alt+Space` 被其他软件占用 | 热键注册失败 | B2 原型先实测；失败就换组合并在设置里暴露 |
| Node 子进程生命周期难管（崩溃残留、僵尸进程） | 常驻不可靠 | B2 原型专门验证；必要时退到 B1-b sidecar |
