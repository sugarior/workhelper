**目标**：`Ctrl+Alt+Space` 在任何程序里按下去，快记窗立刻出现；输入完窗口消失，**原来的编辑位置不丢**。

| 要装 | 用途 | 状态 |

| **MSVC 生成工具**（VS 2022 Build Tools，勾「使用 C++ 的桌面开发」） | Rust 在 Windows 的链接器 | ✅ 已装 |
| WebView2 | 界面渲染引擎 | ✅ 已装 154.0.4258.53 |

**工具链验证方式（不要只看版本号）**：实际编译并运行一个 Rust 程序 ——
只查 `rustc --version` 发现不了链接器问题（`link.exe not found` 只在真正链接时才暴露）。

### B1 架构决策：Node 内核怎么进桌面壳（未决项 D3）

Tauri 壳是 Rust + WebView，而内核是 Node。有三种接法：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **B1-a 独立 Node 进程** | 外壳拉起系统已安装的 Node | 内核**零改动**；崩溃互不影响 | 要求目标机器已装 Node —— **分发场景下不成立** |
| **B1-b Node 随包** | 把 Node 运行时与内核作为**资源**打进安装包，外壳从资源目录拉起 | **用户无需装 Node** | 安装包 +30–40MB |
| B1-c 内核搬到 Rust | 用 Rust 重写数据层 | 单进程、最省内存 | **等于重写整个已验证的内核**，342 项测试全部作废 |

**决策：分两种场景，共用同一份内核代码**（用户确认要"打包安装运行"，因此 B1-b 是必需项）：

| 场景 | 用哪个 | 理由 |
| --- | --- | --- |
| **开发时** | **B1-a**（系统 Node） | 改内核后无需重新打包，迭代快 |
| **打包分发** | **B1-b**（Node 随包） | 用户双击安装就能用，不需预装任何东西 |

> **为什么明确否决 B1-c**（用户曾问"是不是要先移植到 Rust"）：
> 内核是**342 项测试验证过**的资产，用 Rust 重写等于把它全部作废；
> 而换壳真正需要的只有三件事 —— **拉起子进程、注册全局热键、开无边框窗**，
> 三件都不需要碰数据层。等将来真有性能或分发的硬需求，再单独评估。

**为什么用"资源"而不是 Tauri 的 sidecar（`externalBin`）**：
两者差别只在"谁负责找路径"。sidecar 要额外装 `tauri-plugin-shell`、配 `externalBin`、
并在构建时按目标三元组重命名文件；资源方式只是把 Node 可执行文件放进资源目录，
外壳用 `Command::new(<资源目录>/node/node.exe)` 拉起 —— **依赖更少、路径更透明**。
Node 是 MIT 许可，随包分发没有问题。

#### B3 的一个已知缺陷（**必须在打包改造中一并解决，不要单独修**）

**症状**：快记窗保存后不隐藏，停在被 `.closing` 设成透明的状态 —— 用户看到**黑屏**。

**根因**：`capture.js` 靠 `window.close()` 收窗。那在浏览器里是对的（它的注释也写着
"只有由脚本打开的窗口才允许被脚本关闭"），但 **Tauri 的 WebView 不认这句** ——
窗口是 Tauri 建的，不是 `window.open()` 开的。

**试过并失败的三种 Tauri 侧方案**（都**静默失败**，没有报错）：

| # | 方案 | 失败表现 |
| --- | --- | --- |
| 1 | `setup()` 里 `eval()` 替换 `window.close` | 页面已拿到原生引用，替换太晚 |
| 2 | `WebviewWindowBuilder::initialization_script` 注入替身 | 可见性时间线证明脚本从未执行 |
| 3 | 轮询 DOM 读 `.closing` 类 | `eval_with_callback` 的回调从未触发 |

**诊断得到的确定结论**：同一时刻、同一窗口，`eval` 调用返回 `Ok` 但实际不执行、
回调不触发；而 `eval_with_callback` **在窗口创建 4 秒后是正常的**。
同时**主窗口的 JS 通道完全正常**。两者唯一差别：

| 窗口 | 创建方式 | JS 通道 |
| --- | --- | --- |
| 主窗口 | **配置里声明** | ✅ 正常 |
| 快记窗 | **运行时创建 + 外部 URL** | ❌ 不可靠 |

> **因此结论是：不要为"运行时创建 + 外部 URL"这个即将被替换的加载方式继续写代码。**
> 用户已确认"界面随包自带"（见 §4.1），届时两个窗口都会改从**应用协议**加载 ——
> 那正是 JS 注入本该正常工作的路径。改完再验证一次即可，预期直接消失。

## 4.1 打包分发方案（用户确认，M1 交付形态）

**目标**：产出一个 NSIS 安装包，**别人拿到双击安装就能用**，不需要预装 Node 或 Rust。

### 五项已确认的决定

| # | 决定 | 说明 |
| --- | --- | --- |
| 1 | **自带 Node 运行时** | 打进安装包（+30–40MB）。用户不需要装任何东西 |
| 2 | **数据默认 `%APPDATA%\WorkHelper`，但可配置** | 安装到 `Program Files` 后程序目录不可写，因此不能放程序目录旁 |
| 3 | **界面随包自带，只有 API 走 Node** | 界面瞬间打开、零延迟；快记窗不再受"Node 正在启动"影响 |
| 4 | **NSIS 安装包** | 有开始菜单与卸载项，可选开机自启 |
| 5 | **首次启动显示主窗口** | 装完双击就能用，不让人以为没装上 |

### 3 与 4 引出的两个连带改动（不是可选项）

**① 界面与 API 会变成跨源，必须加 CORS**

```
界面  tauri://localhost/index.html      ← 安装包内
API   http://127.0.0.1:7317/api/...     ← Node 服务
```

两者**不同源**，浏览器规则要求 Node 返回 CORS 头，否则所有数据请求被拒。
WebView2 同样适用这条规则。做法：`src/ui/server.ts` 只对**自家源**返回
`Access-Control-Allow-Origin` 并处理 `OPTIONS` 预检。因为服务只监听 `127.0.0.1`，
外部本来就不可达，这是安全的。

**② `api.js` 必须知道服务器地址**

现在它用相对路径 `/api/...`（与 Node 同源所以能工作），界面自带后必须改成显式地址。
做法：**外壳启动 Node 后把端口注入页面**，`api.js` 读注入值；读不到就退回
`location.origin`（**浏览器里开发时行为完全不变**）。

### 目录与路径（打包后）

| 用途 | 位置 | 说明 |
| --- | --- | --- |
| 程序文件 | `%LOCALAPPDATA%\Programs\WorkHelper\`（NSIS 默认） | 含 `workhelper-shell.exe` |
| Node 运行时 | `<程序目录>\resources\node\node.exe` | 作为**资源**随包，不走 Tauri sidecar |
| 内核源码 | `<程序目录>\resources\src\` | `.ts` 直接由 Node 26 剥离类型运行，**无构建步骤** |
| 界面静态资源 | 打进 `workhelper-shell.exe` | 由 Tauri 的应用协议提供 |
| **数据** | `%APPDATA%\WorkHelper\data\` | 默认值，可由 `--data` 或设置改写 |

### 4.1.1 怎么验证"打包真的自包含"（不重开虚拟机/账户，不清 PATH）

**用户明确要求：在当前环境继续开发，非必要不重开虚拟机或账户、不清 PATH。**
这个要求是对的 —— 原来的方案（虚拟机/另一账户）成本过高，而且**验证得比需要的弱**：
虚拟机只告诉你"坏了"，不告诉你**坏在哪一项**。

**真正的风险不是"别的机器缺什么"，而是"我这台机器上的外部依赖掩盖了打包缺陷"。**
例如外壳的 `find_node()` 先查 PATH，那么**打包时漏掉 Node 也测不出来** ——
它会静默用系统的 Node 跑起来。

#### 措施一：让依赖无法隐藏（设计约束，不是测试技巧）

| 约束 | 理由 |
| --- | --- |
| **打包态只用随包 Node，完全不查 PATH** | 消除"静默回退到系统 Node"。找不到就报错，而不是悄悄用别的 |
| **不再硬编码 `D:\AppGallery\node.exe`**（当前代码里有） | 那是本机的临时位置，写死只会掩盖问题。开发态用 PATH 查找即可 |
| **数据目录由外壳显式传给内核**（`--data`） | 不依赖内核自己推导，避免"装到 Program Files 后不可写" |
| **界面资源路径在打包态解析到资源目录，找不到就报错** | 避免"编译时注入的仓库根"在打包后指向不存在的路径 |

#### 措施二：启动自检（缺什么就说什么）

外壳启动时按顺序检查，**任何一项不过就明确报错并退出**，不进入半可用状态：

| 检查项 | 失败时的提示要点 |
| --- | --- |
| 随包 `node.exe` 存在且可执行 | 说清期望路径；安装损坏 → 建议重装 |
| 内核资源树存在（`resources/src/ui/main.ts`） | 同上 |
| 数据目录**可写**（实际写一个临时文件验证） | 说清目录路径与失败原因（权限/只读盘） |
| 端口 7317 空闲 | 说清被哪个进程占用（若能取到），而不是静默换端口 |
| 界面静态资源可解析 | 同上 |

#### 措施三：`--diagnose` 打印全部解析路径

一条命令输出所有路径与检查结果，**它本身就是验证工具**：
比"界面能不能打开"精确得多，也让用户报障时能直接贴出来。

#### 验收标准（在本机就能做，且是决定性的）

```
1. 用打包产物启动 → 应正常
2. 把 D:\AppGallery\node.exe 临时改名 → 再启动打包产物 → 仍应正常
   ← 决定性验证：证明产物真的自包含
      （官方安装器不往 D:\AppGallery 放 Node，因此这不算"清理 PATH"）
3. 故意删掉资源目录里的 node.exe → 启动应明确报错"缺 node" → 证明自检有效
4. 恢复上述临时改动
```

**第 2 条是关键**：它证明打包产物不依赖任何外部 Node。**第 3 条**证明失败不会被静默吞掉。
