## 1. 背景与问题

我在日常工作中反复遇到四个问题，它们互相加剧：

| # | 问题 | 具体表现 |
| --- | --- | --- |
| P1 | **想法记不下来** | 正在做 A 时被口头交代 B，或突然想到 C；打开待办软件、选清单、填字段、保存——步骤太多，于是先记在纸上/脑子里，然后就丢了 |
| P2 | **清单只会堆积** | 攒了几十条"要做的事"，但都停在一句话粒度，不知道从哪下手，看不清"今天做什么" |
| P3 | **跟进靠回忆** | 一件事推进了三次，中间结论散在聊天记录、便签、脑子里的临时记忆；再捡起来要重新推理一遍 |
| P4 | **复盘是编的** | 写日报/周报时想不起这周干了什么，只能凭印象凑，过程细节全丢了 |

**根因判断**：不是我懒，而是现有工具把「记录」和「结构化」这两件成本完全不同的事**压在同一个动作里完成**——想快速记，就得先想清楚它属于哪个项目、什么优先级、什么时候做。这一步的摩擦力，就是所有记录习惯死掉的地方。

## 2. 目标与非目标

### 2.1 目标

**一句话目标**：做一个常驻 Windows 桌面的个人工作秘书，让我能在**不打断当前工作**的前提下把任何东西丢进去，然后由它（必要时借 AI）帮我把混乱的输入整理成可执行、可跟进、可复盘的结构。

拆成三条可验证的目标：

- **G1 · 零摩擦捕获**：任何念头，从"意识到要记"到"记完并回到工作"，**不超过 3 秒、不切换窗口、不选分类**。
- **G2 · 结构化兜底**：堆积的收件箱能通过一次操作（AI 拆分 + 我确认）变成有层级、有验收标准、有排期的任务树，而不是靠我逐条手工整理。
- **G3 · 记录即资产**：每次推进的备注和每日日志天然沉淀为单一事实源，写日报/周报时是**导出**而不是**回忆**。

### 2.2 非目标（明确不做，防止范围失控）

| 不做 | 原因 |
| --- | --- |
| 多人协作 / 任务分派 / 权限 | 只服务我一个人，引入账号与并发会拖垮体验 |
| 手机端 / 多设备同步 | v1 单机；同步会带来冲突合并、鉴权、部署一整套复杂度 |
| 习惯打卡、番茄钟、时间统计 | 本次明确不需要（无计时、无精力/情绪记录） |
| 云账号与 SaaS 登录 | 数据主权是选它的理由之一，不想被订阅和隐私条款绑架 |
| AI 全自动接管我的任务表 | 明确选择"按需调用 + 人工确认"，避免不可信自动化带来的失控感 |
| 通用笔记系统 / 知识库 | 只做"与工作和任务有关的记录"，不做第二大脑 |

## 3. 使用者与使用场景

### 3.1 使用者

只有一个人：需要同时推进多件事、频繁被打断、且需要向上汇报进展的知识工作者。环境为 Windows 单机，数据不离开本机（AI 拆分时按需发送最小片段）。

### 3.2 核心场景

**S1 · 随手一记（每天 10–30 次）**
> 正在写代码，同事过来说"下周三之前把接口文档给一下"。
> 按 `Ctrl+Alt+Space` → 输入框已聚焦 → 敲"接口文档 下周三 给张三" → `Enter`。窗口消失，人没离开键盘。

**S2 · 每日定盘（每天 1 次，约 5 分钟）**
> 打开收件箱，看到一天攒下的 8 条碎片。选中其中 3 条点「帮我拆」（AI，M2），弹出可编辑的子任务预览：包含步骤、验收标准、建议排期。删掉两条不认可的，确认写入。把剩下 2 条拖进已有项目，3 条判定为垃圾直接**丢弃**。
>
> **手工通路（当前可用形态）**：没有 AI 时，我把碎片逐条转成任务、指定归属项目，再在项目里逐条补子任务。这条通路必须在 AI 缺席时也完整可用——它是保底手段，不是临时方案。

**S2b · 确认没有遗漏（每天 0–1 次，约 1 分钟）**
> 打开「全部」视图，看到的不是"今天要做的"，而是**所有还没结束的事**：逾期 2 条、今天到期 3 条、没有排期的 7 条、进行中 2 条、阻塞 1 条。
> 我扫一眼那 7 条没有排期的，挑 3 条排进今天，剩下 4 条确认它们确实不急。
> **关键**：这 7 条从来不会从我的视野里消失——它们只是"还没排期"，不是"不存在"。

**S3 · 推进与复盘（随时 + 每天下班前）**
> 任务推进到一半卡住了：在悬浮小组件里点开那条任务 → 追加一句"卡在等法务确认，已催"。
> 下班前弹提醒，打开当日日志：已完成 4 条、新增 3 条、顺延 2 条、卡点 1 条已自动汇总好，我补两句说明，保存。

**S4 · 随手存指针（每天 0–3 次）**
> 在飞书里看到一份要用的设计文档，或者在资源管理器里找到了那个项目目录。
> 按热键唤出速记板 → 粘贴链接或路径 → 后面补一句"这是迁移方案 v3" → `Enter`。
> **不选任务**（此刻我只想把它存下来）。它落进收件箱，等我下一次整理时再关联。

**S5 · 开工（每天 1–3 次，这是资料的价值兑现点）**
> 要开始做「Q3 数据平台迁移」了。在「全部」或「今日」里找到这条任务，点开资料折叠行：
>
> ```
> 📎 资料 3 条
>   ☑ D:\work\q3-migration            工作区
>   ☑ \\nas\设计\迁移方案_v3.docx       最新方案
>   ☐ https://xxx.feishu.cn/docx/...   立项会纪要
>   [打开选中的 2 项]
> ```
> 勾两个、点一下 → 资源管理器打开工作区、Word 打开方案文档。**不用再翻聊天记录找路径。**

**S6 · 写周报（每周 1 次，这是 P4 痛点的兑现场景）**
> 周五下午要交周报。不再靠回忆 —— 打开「全部」页签，切到**已完成**，时间范围选「最近 7 天」：
>
> ```
> 已完成 · 最近 7 天 · 共 14 条（任务 6 · 子任务 8）
>   [全部未结束] [已完成]        最近 7 天 | 全部 | 自定义
>
>   2026-09-30  周三
>     ☑ 写迁移方案                     Q3 数据平台迁移
>     ☑ 盘点现有表                     Q3 数据平台迁移 › 调研阶段
>   2026-09-29  周二
>     ☑ 交接口文档                     毕业论文
> ```
> 一眼扫完，照着写。**这就是 G3 说的"导出而不是回忆"** —— 不必等 M2 的 Markdown 导出。

**S7 · 清理与找回（偶尔）**
> 整理收件箱时手快点了「丢弃」，把一条有用的东西扔了。
> 主界面右上角 → **回收站** → 切到「**已丢弃**」→ 找到它 → **放回待处理**。
> 丢弃的条目不会自动消失 —— 那是我主动做的判断，程序不该替我抹掉。

## 4. 核心概念模型

只保留六个概念，全部围绕"从混乱到有序"的流水线设计：

```
【捕获】收件箱 Inbox ──分类──> 【结构】项目 → 任务 → 子任务（三级树）
                  │                        │
                  │                        ├── 进展记录 ProgressEntry（每次推进一条，带时间戳）
                  └──归档──> 资料 Material ─┤
                            （必须挂靠）    └── 资料是"这件事的东西在哪里"的指针
                                     │
                               ──汇总──> 每日日志 DailyLog（自动汇总 + 人工补录）
                                               │
                                         ──> Markdown 导出（日报 / 周报）
```

| 概念 | 定义 | 关键属性 |
| --- | --- | --- |
| **收件箱 Inbox** | 一切未分类输入的默认落点。**唯一要求是"必须能被清空"** | 原始文本、创建时间、可选标记（待办 / 资料） |
| **项目 Project** | 一件事、一个阶段或一条工作线（如"Q3 数据平台迁移"） | 名称、状态、起止、目标描述、进度（由任务汇总） |
| **任务 Task** | 可独立交付、有明确完成判据的工作单元 | 标题、状态、优先级、**截止日期（可空）**、预估、所属项目（**可空**）、标签、来源 |
| **子任务 Subtask** | 任务下的可执行步骤 | 标题、状态、顺序、（可选）截止时间、（可选）验收标准 |
| **进展记录 ProgressEntry** | 挂在项目/任务/子任务任意一层上的带时间戳备注 | 内容、时间、类型（进展 / 卡点 / 决定 / 等待他人） |
| **每日日志 DailyLog** | 一天的收口，系统自动汇总 + 我手工补录 | 当日完成、新增、顺延、卡点、明日计划、自由正文 |
| **资料 Material** | **"这件事的东西在哪里"的指针**：工作区目录、文件、网址。<br>**必须挂靠到至少一个任务或项目**，否则就是垃圾 | 标题、若干**入口**（每个入口 = 类型 + 目标 + 可选注释）、关联的任务/项目（可多个）、顺序 |

**对象关系**：一个项目包含多个任务；一个任务包含多个子任务；任意层级都可挂进展记录；
每日日志通过时间维度聚合所有对象；**一条资料可关联多个任务/项目**（多对多）；一条资料含多个**入口**。

> **两个字段必须可空，这是刻意的**：`任务.截止日期` 与 `任务.所属项目`。
> 捕获时不允许要求分类或排期（§6.2），因此任何"必须有归属或必须有日期"的约束
> 都等于在登记时逼我做决定。代价是这类任务必须靠 §6.6 的可见性约束兜住。

#### 4.1 资料（Material）的定位 —— 本项目最重要的一次需求澄清

资料的定义在第一版里写的是"与工作相关的非任务信息：会议纪要、链接、截图、文件"。
**这个定义太宽泛，等于没有定义**，它会让资料退化成一个什么都装的盒子。
真实用途是另一回事：

> 任务「Q3 数据平台迁移」→ 资料：工作区 `D:\work\q3-migration`、设计文档 `\\nas\设计\方案_v3.docx`、飞书文档链接
> **点一下就能打开，不用再翻聊天记录找路径。**

因此资料的定位是**指针，不是内容**：

| 是 | 不是 |
| --- | --- |
| 记录"东西在哪里"（路径、URL） | 知识库、笔记系统、第二大脑 |
| 服务于某个任务/项目的开工与查找 | 可独立存在的资料库 |
| 稀缺（一天 0–3 条）、精确 | 越多越好的归档桶 |
| **必须挂靠**，否则成为堆积的垃圾 | 允许游离 |

**由此推出三条硬规则**：

| # | 规则 | 理由 |
| --- | --- | --- |
| M1 | **资料必须挂靠到至少一个任务或项目** | "一旦资料无关联就会成为堆积的垃圾，难以整理" |
| M2 | **转资料时必须选择目标，且绝不自动关联"当前正在做的任务"** | 自动挂错任务的犯错成本（之后找不到）远高于多选一次的成本 |
| M3 | **只存指针与注释，不存文件本体** | 避免文件落盘、去重、备份、清理这一整套工程负担；粘贴路径比上传文件更符合"零负担" |

**M2 的直接后果**：收件箱里的「存为资料」按钮**不能一点就存**，必须先弹出目标选择。
这与"存为资料"作为一条独立路径不冲突——资料**在收件箱阶段允许无关联**（它是待处理的输入），
但**一旦成为正式资料就必须有关联**。

**M2 的延伸价值**：资料持有工作区地址后，任务就变成了**开工入口** ——
点任务 → 看到相关资料 → 多选打开 → 直接开始干活。这也是"必须挂靠"从整洁偏好升级为功能前提的原因：
没有关联，程序就不知道该打开什么。

#### 4.2 资料的六条设计决策（逐条确认）

这是继"可见性约束"（§6.6）之后**第二处由真实使用倒逼出来的需求补完**。
第一版对资料的定义过宽，导致它退化成一个什么都装的盒子 —— 而"没有组织规则的盒子"最终必然变成垃圾堆。

| # | 决策 | 理由 |
| --- | --- | --- |
| **D1** | 资料类型只有三种：**本地目录 / 本地文件 / 网址**。网址不单列"网络资料" —— 飞书文档、Overleaf 这类网址**本身就是工作区** | 按"是否本地"分类没有意义，有用的是"怎么打开" |
| **D2** | 一条资料含 **1..N 个入口**；入口是**独立结构**（可各自带注释、可排序） | 入口要能**按常用程度排序**，所以不能塞进一个 JSON 字段，必须是子表 |
| **D3** | **不做分层**（不设"资料集 > 资料项"）；需要同时打开多个时用**多选**实现 | 分层会带来手动归类成本；多选已满足"恢复工作区"，且少一层维护 |
| **D4** | 速记板支持**多行粘贴**，每行一个入口，行内其余文字成为**该入口的注释**；注释粒度由我输入时决定 | 注释归属需要灵活（三个链接里可能只有中间那个要说明）；后续可让 AI 分析 |
| **D5** | **只存指针与注释，不存文件本体**。速记板可粘贴路径，可拖入文件（**真实路径待 M1 的 Tauri 外壳**） | 浏览器拿不到拖入文件的真实路径（安全限制），只能拿到文件名；粘贴路径现在就能用 |
| **D6** | 打开方式：**单个打开** + **多选批量打开** + **复制路径**（兜底）。**不做自动打开** | 内网路径或未挂载盘符时"打开"会失败，复制路径保证信息仍可用 |

**状态机（最小集）**：
- 任务：`待办 → 进行中 → 阻塞 → 完成 / 取消`（`阻塞` 必须能填原因，这是 S3 的关键）
- 子任务：`待办 → 完成`
- 收件箱：`未处理 → 已分类 / 已丢弃`

**术语约定（必须严格遵守，否则会持续歧义）**：

| 词 | 含义 | 结果 |
| --- | --- | --- |
| **归档** | 把信息留存为**资料** | 生成资料记录（含入口），**必须挂靠任务/项目** |
| **丢弃** | 判定为垃圾，不值得留存（**主动判断**） | 收件箱条目 `status = 'archived'`，不生成任何实体 |
| **删除** | 我根本不该记它（**误录纠正**） | 软删除（`deleted_at` 置值），进回收站，**30 天后自动清理** |
| **彻底删除** | 物理删除，**不可恢复** | 需二次确认。这是全系统唯一不可逆操作 |
| **放弃** | 任务不再做了 | 任务 `status = 'cancelled'`，保留记录与历史进展 |

> 这五个词**互不通用**。早期文档曾用"归档"表达"丢弃"，属于措辞错误，已修正。

**三种"消失"的区别（极易混淆，必须分清）**：

| 操作 | 数据是否还在 | 能否找回 | 是否自动过期 |
| --- | --- | --- | --- |
| **丢弃** | 在（只是状态变了） | 能：回收站页的「已丢弃」筛选 → 放回待处理 | **否**（理由见下） |
| **删除** | 在（软删除） | 能：回收站页的「已删除」筛选 → 恢复 | 是，30 天 |
| **彻底删除** | **不在** | 否 | —— |

> **为什么丢弃不自动过期**：丢弃是**我主动筛掉的**，自动删除等于悄悄抹掉我的判断记录；
> 回收站里的东西则是"我不小心弄掉的"，才需要自动兜底 —— 两者的风险方向相反。
> 因此丢弃的条目长期保留、**可被搜索**，但要提供**手动**「彻底删除」作为清理出口。

**"删除"的守卫（防止抹掉处理痕迹）**：

已处理的条目（`status = 'converted'` 或 `'archived'`）**不允许删除**。
删除的语义只适用于**待处理**的条目 —— 对已处理的条目删除等于抹掉历史，
要撤销就该用「撤销上一次分类」，要清掉垃圾就该用「丢弃」。

**资料相关的术语（避免与上表混淆）**：

| 词 | 含义 |
| --- | --- |
| **入口 Entry** | 资料里的一个可打开项：本地目录 / 本地文件 / 网址。一条资料可含多个入口 |
| **挂靠** | 资料与任务/项目建立关联。一条资料可挂靠多个，**且必须至少一个** |
| **开工** | 从任务上多选资料入口并一次性打开（手动触发，不自动） |

## 5. 功能需求

优先级定义：**P0 = v1 必须有**，缺了就不算可用；**P1 = v1 应有**；**P2 = 后续迭代**。

### 5.1 P0 — 捕获层

| 编号 | 功能 | 设计要点 | 验收标准 |
| --- | --- | --- | --- |
| F-01 | **快记浮窗** | 全局快捷键 `Ctrl+Alt+Space` 唤出无边框小窗，输入框自动聚焦 | 按下热键到可输入 **≤ 150ms**；`Enter` 保存并关闭，`Shift+Enter` 换行，`Esc` 取消不留痕 |
| F-02 | **速记板（多输入）** | 芯片：`收件箱`(默认) / `资料`；**不做二级选择、不弹出项目选择器**。<br>**支持粘贴多行**，每行一个入口：识别出路径/链接的部分成为入口，行内其余文字成为**该入口的注释**。<br>**不存文件本体**，只存指针与注释 | 从输入到入库 ≤ 2 次按键；多行输入能正确拆成多个入口；识别不出路径/链接的行**原样存为普通收件箱条目**（绝不丢内容） |
| F-03 | **无干扰反馈** | 保存后不弹确认框，仅在浮窗位置播放 300ms 的收起动画 + 可选轻提示音 | 不抢焦点、不打断当前窗口输入 |
| F-04 | **收件箱视图** | 列表 + 清空流程。每条可：`转任务`（可指定项目）/ **`转项目`** / **`存为资料`** / `丢弃` / **`删除`**（删除=误录纠正，进回收站）；支持多选批量 | 20 条收件箱可在 5 分钟内处理完；**必须提供删除入口**；<br>**`存为资料` 必须先选目标**（见 F-11 与 M2 规则） |
| F-05 | **全局快捷键** | 可在设置中自定义，检测冲突并提示 | 冲突时给出明确提示而非静默失效 |

**F-04 的两个动作需要明确定义（早期文档只在场景里提过，功能清单里漏了）**：

| 动作 | 含义 | 结果 |
| --- | --- | --- |
| **转项目** | 这条碎片本身就是"一件事" | 以碎片标题为名**新建项目**；后续在项目页里逐步加任务与子任务 |
| **并入已有项目** | 这条碎片属于某个已有项目 | 它不是独立动作，而是 `转任务` + 选中项目选择器；**批量操作时尤其顺手** |

> **为什么不做"任务升级为项目"**：碎片转成任务时它是**叶子节点**（无子任务、无进展），
> 所以"该是项目却当成了任务"的代价只是重打一次标题、约 30 秒。
> 反过来给叶子任务做升级，收益极小、语义复杂（子任务与进展记录是否跟随？），故不做。
> 若将来真出现痛点，那时任务可能已带子任务与进展，才值得认真设计。

| F-13 | **资料：速记与整理** | 速记板支持**粘贴多行**（每行一个入口，行内非路径文字成为该入口的注释）；支持从资源管理器**拖入文件/文件夹** —— **浏览器阶段无法取得真实路径，此能力待 M1 的 Tauri 外壳**；<br>整理收件箱时，`存为资料` 弹出目标选择（可多选任务/项目） | 粘贴三行路径 → 生成 3 个入口，注释归属正确；<br>识别不出路径的行原样保留为普通条目，**绝不丢内容** |
| F-14 | **资料：浏览与关联视图** | 独立的资料页签（**默认显示，设置里可隐藏**）：按时间倒序列出，可筛"未挂靠"，可改/追加挂靠；<br>任务/项目详情里以**折叠行**展示：`📎 资料 3 条` → 展开后多选打开 | 资料页能处理未挂靠项；任务上不因资料多而变长 |
| F-15 | **全局搜索** | 搜任务、子任务、进展记录、日志、资料的**标题/注释/路径** | 1000 条数据下结果 **≤ 200ms** |

**资料模块的边界（明确不做，防止膨胀）**：

| 不做 | 原因 |
| --- | --- |
| 存文件本体（上传/截图/附件落盘） | M3 规则：只存指针。避免落盘、去重、备份、清理整套工程负担 |
| 文件夹树 / 标签体系 / 双向链接 | 资料是稀缺的指针，不是知识库。组织靠"挂靠到任务" |
| 自动打开工作区（进入任务就批量打开） | 与"自动化都要经我同意"一致；且打开一堆当下不想看的东西会打断心流 |
| 一条资料内部再分层（资料集 > 资料项） | 分层会带来手动归类成本；"同时打开多个"用**多选**实现即可 |
| 入口自动抓取网页标题 | 价值有限、引入网络依赖；注释由我一句话写清更准 |

## 6. 关键交互约定（UI/UX 契约）

这几条是产品的"手感"，实现时必须守：

#### 6.1 不抢焦点

**浮窗永远不抢主窗口焦点**：呼出快记后，原来的编辑器光标位置不丢。

#### 6.2 默认值必须正确

不选分类就是收件箱，不选时间就是今天，不选优先级就是中。**永远不强迫我在记录时做决定。**

#### 6.3 不存在"保存失败"

先落本地磁盘再处理业务；网络与 AI 全部是异步旁路，断网也能记。

#### 6.4 所有 AI 输出都是建议，不是命令

预览 → 确认 → 写入，且写入后可整体撤销。

#### 6.5 积压要看得见，但不催我

**收件箱可以长期不清空，但必须能一眼看到积压了多少**——用数字刺我，而不是用红色警告烦我。

### 6.6 可见性约束（★ 由契约 2 推导出的硬要求）

> **任何未结束的任务，在界面上必须至少有一个地方能看到它。**

这条不是凭空加的，它是契约 2 的**必然推论**：

既然捕获时不允许要求分类或排期，那么"既无截止日期、也不属于任何项目"的任务
就是一个**合法且常见**的状态。如果界面上没有任何视图收录这类任务，
它就会永久沉底——**契约 2 的"零门槛捕获"反而变成了"零门槛丢事"**。

因此以下三条都是硬性要求：

| # | 要求 | 违反后的表现 |
| --- | --- | --- |
| V1 | 存在一个列出**所有未结束任务**的视图（F-09），不依赖截止日期或项目归属 | 无日期无项目的任务永远看不到 |
| V2 | 任何聚合视图**不得自相矛盾**：若某处显示"未结束 N 条"，则能看到这 N 条 | 页面顶上说"未结束 3"，下面写"今天没有待办" |
| V3 | 未结束任务的数量必须在主界面常驻可见（徽标或计数），不让积压静默增长 | 我根本不知道有东西在沉底 |

**验收方式**：造 3 条任务——① 无截止日期无项目 ② 截止日期在未来 ③ 属于某项目——
三条都必须能在不看 CLI 的情况下于界面上找到。这条已作为 M0 的验收项。

## 7. 数据与技术方案（初稿，技术栈由我决策）

### 7.1 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 桌面外壳 | **Tauri 2** | 安装包约 10MB、常驻内存低，适合 7×24 挂托盘；原生支持托盘、全局快捷键、多窗口、开机自启 |
| 界面 | TypeScript + React + Vite | 生态成熟，浮窗/组件式 UI 开发快 |
| 本地存储 | **`node:sqlite`（Node 26 内置，WAL 模式）** | 已实测本机 `node:sqlite` 可用：**零原生编译依赖**，不装 `better-sqlite3` 也能用 SQLite + FTS5，避免 node-gyp/MSVC 带来的构建麻烦 |
| 数据目录 | **工程目录下 `data\`** | `data/workhelper.db` + `data/attachments/` + `data/backups/`；**必须写进 `.gitignore`**，避免数据被提交 |
| 数据可读性 | SQLite 为主 + **Markdown 导出** | 数据库保证查询性能，导出保证"哪天不用这个软件了，资料还在" |
| AI | **DeepSeek 官方 API**（OpenAI 兼容协议） | 已定；接口按 OpenAI 兼容层抽象，换供应商零成本 |
| 备份 | 启动时自动快照，保留最近 7 日 + 4 周 | 单机数据的唯一风险是硬盘和误删 |

### 7.2 架构原则：内核与界面分离

必须在第一行代码就成立的一条：**数据模型与业务逻辑不依赖桌面容器**。

```
┌─────────────────────────────────────────────┐
│  界面层（可替换）                             │
│  主窗口 / 快记浮窗 / 悬浮小组件 / 托盘菜单      │
└──────────────────┬──────────────────────────┘
                   │  本地 IPC（命令 + 事件）
┌──────────────────▼──────────────────────────┐
│  内核层 WorkHelper Core                      │
│  ┌─────────┬─────────┬──────────┬────────┐  │
│  │ 任务域   │ 日志域   │ 收件箱域  │ 搜索域  │  │
│  └─────────┴─────────┴──────────┴────────┘  │
│  Repository（唯一写入口）+ 事件总线            │
└──────────────────┬──────────────────────────┘
                   │
        ┌──────────▼──────────┐
        │ SQLite + 附件目录     │
        └─────────────────────┘
                   ▲
                   │ 可选：CLI / MCP（P2）
```

好处很实际：将来想要"在 DSH 里也能登记任务"或"用命令行批量导入"，只需在内核上加一个适配层，不用重写业务逻辑。

| **M3 · 打磨** | 性能、备份恢复、导入导出、P2 候选按需挑选 | 装机即可长期使用，无数据丢失事故 |

> **M0 的完成判据里"不丢数据"包含两层含义**：
> 一是物理上不丢（SQLite + 备份 + 软删除，已有 220 项测试覆盖）；
> 二是**逻辑上不丢**——任务不会因为"没排期"而从视野里消失（§6.6）。
> 后者曾被我忽略，导致界面顶上说"未结束 3"、下面却说"今天没有待办"。

**R1 值得单独强调**：它不是实现 bug，而是**需求漏了一个视图**。契约 2（"永远不强迫我在记录时做决定"）必然产生"无日期无项目"的任务，但文档从没回答"这类任务在哪里能看到"。我按字面实现 F-08，结果就是那个自相矛盾的页面。**这条教训是：每写一条"降低输入门槛"的契约，都必须同时回答"这些输入事后在哪里被收容"。**

**R9 与 R10 的共同规律**：两者都属于**"场景里描述了、条款里没确认"**。
场景是叙事，容易被写得比实际约定更丰满，而实现只认条款。
**对策：新增或修改场景时，必须同时检查功能清单里是否有对应条款。**

#### 9.3.1 三次同类问题的归纳（★ 固定检查项）

R1、R10、R12 是**同一类失败的三次重复**，必须当成一条固定检查项，而不是三次偶然：

| # | 目标层写了什么 | 条款层缺了什么 | 后果 |
| --- | --- | --- | --- |
| **R1** | 契约 2"永远不强迫我在记录时做决定" | 没回答"无日期无项目的任务在哪看" | 任务沉底，"随手记"变成"随手丢" |
| **R10** | "资料可关联任务/项目"、"记录不能成为负担" | 没说关联是**必须**的，也没定位资料是什么 | 资料退化成垃圾堆 |
| **R12** | **P4**"复盘是编的"、**G3**"写日报是**导出**而不是**回忆**" | 功能清单里没有任何跨天总览；唯一的周报导出在 M2，周度回顾被划为 P2 | **P4 这个核心痛点当前没有解法** |

**共同规律**：

> **目标层（目标 / 痛点 / 契约）承诺的能力，必须在功能清单里有对应条款落地；
> 否则它不会实现 —— 而且不会有人发现，因为实现者只读条款。**

**由此定下的固定检查项**（每次改需求都必须过一遍）：

| # | 检查 | 对象 |
| --- | --- | --- |
| C1 | 每条**契约**（§6）是否都有条款承接"这些输入事后在哪里被收容" | §6 ↔ §5 |
| C2 |每条**目标 / 痛点**（§1、§2.1）是否都有条款支撑 | §1/§2.1 ↔ §5 |
| C3 | 每个**场景**（§3.2）里描述的动作是否都在功能清单里 | §3.2 ↔ §5 |
| C4 | 每条新条款的**验收标准**是否可测量（否则等于没写） | §5 内部 |

**R12 的处理**：新增 **F-09b 已完成总览**，把"复盘不用回忆"在 M0 就落地，
不再依赖 M2 的 Markdown 导出。同时把 §5.6 的"周度回顾视图与趋势"从 P2 里**划掉**
——它的核心能力已由 F-09b 覆盖，剩下的"趋势"才是 P2。

| 风险 | 后果 | 对策 |

| **记录习惯养不成**（最大风险，也是同类工具的头号死因） | 做完了却不用 | G1 指标当硬门槛；M1 结束后做一周真实使用复盘，不用就改，不硬撑 |

| **资料退化成垃圾堆**（新识别） | 无关联的资料无法组织、无法利用，最终成为放着不看的堆积 | §4.1 三条硬规则：**必须挂靠**、**转资料必选目标且不自动关联**、**只存指针**；F-14 资料页提供"未挂靠"筛选与补救挂靠 |
| **资料挂错任务** | 比"多选一次"严重得多：之后想找这条资料会找不到 | **绝不自动关联"当前正在做的任务"**（规则 M2）。宁可多选一次，不承担静默挂错的风险 |
